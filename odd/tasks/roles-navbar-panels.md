# Navegación por roles + paneles de usuarios y levantamientos

**Objetivo**: navbar única por sesión con avatar/perfil/logout, menú según rol (encuestador: mis registros; admin: listado, dashboard, esquemas, usuarios, levantamientos), panel de gestión de usuarios y panel de levantamientos; listado de registros por dueño.
**Branch**: `feature/gis-platform-v3` · **Runner**: `pnpm typecheck && pnpm test && pnpm lint && pnpm build`.
**Estrategia de entrega**: commits por unidad en la branch actual; PR a decisión del usuario. Pronóstico ~1.600 líneas autoradas en 6 unidades; las 4 unidades de escritura (T2–T5) se delegan en paralelo a writers con superficies disjuntas (Writer trigger a). Primitivas UI: solo `components/ui/*` estándar (heredan S1/S2 de ui-shadcn-landing: tokens de globals.css, sin overrides).

## Specs

- **S1** (verbatim): "el usuario "normal2 sólo ve la navbar con su user, avatar y las opciones de listado o "mis registros", su perfil para actualizar datos y el botón de cerrar sesión." → Navbar compartida (client, `useSession`): el encuestador ve su nombre + avatar (iniciales, primitiva Avatar estándar), "Mis registros", "Perfil" (actualizar datos) y "Cerrar sesión". Ninguna opción de administración. Avatar con DropdownMenu estándar (Perfil / Cerrar sesión).
- **S2** (verbatim): "el usuario administrador ya ve un menú más amplio, ve igual el useravatar, pero tiene todas las demás opciones, listado, dashboard, esquemas, usuarios..." → admin ve: Listado (todo), Dashboard, Esquemas, Usuarios, Levantamientos + Perfil + Cerrar sesión. Los enlaces salen de `permissionsFor`/`isAdmin` (`lib/auth/roles.ts`), nunca hardcodeados por página.
- **S3** (verbatim): "crear un panel de usuarios para poder gestionar los usuarios" → `/admin/usuarios` con gate `usuarios:gestionar`: lista con búsqueda, cambiar rol (`set-role`: encuestador/admin), suspender/reactivar (ban/unban) y crear usuario. Sin eliminar usuarios (destructivo; el ban cubre la desactivación) ni impersonar.
- **S4** (verbatim): "y también el panel de "levantamientos"" → `/admin/levantamientos` con gate `levantamiento:gestionar`: lista, crear y editar levantamiento (nombre, ciudad, totalEsperado) vía nueva ruta PATCH; progreso visible por levantamiento.
- **S5** (verbatim): "los pines colocados, deberían pertenecer a un usuario" → el dueño YA se persiste (`creadoPor`/`actualizadoPor`, `lib/domain/types.ts:101-104`); lo que se añade: filtro `creadoPor` en GET /api/parcelas + índice en `collections.ts`; el encuestador ve solo sus registros ("Mis registros"), el admin el listado completo. La edición queda colaborativa (el modelo de módulos versionados es multi-editor) y el borrado conserva su regla existente (solo el dueño o admin).
- **S6** (implícito): Sin regresiones: suite, typecheck, lint y build pasan; los tests de auth existentes (`auth.test.ts`, `session.test.ts`, `roles.test.ts`) siguen en verde con el plugin admin habilitado.
- **S7** (heredado): toda UI nueva usa primitivas `components/ui/*` sin overrides y tokens de `app/globals.css`; `globals.css` intocable para writers.

Decisiones (asunciones explícitas, no bloqueantes): (a) "mis registros" = `creadoPor === yo` (atribución de captura; la edición multi-editor del modelo de sync no se restringe). (b) Perfil actualiza nombre y contraseña (`updateUser` + `changePassword` de better-auth); cambio de email queda fuera (requiere infra de verificación que no existe). (c) Login redirige por rol: encuestador → `/campo`, admin → `/admin/dashboard` (corrige el "Sin permiso" actual). (d) Gate de dashboard con `levantamiento:gestionar` (ya existente y solo admin); `/api/export` queda session-only — se registra como observación, no se cambia sin pedido. (e) La landing mantiene su header público sin sesión. (f) Sin avatares con imagen: iniciales (el modelo de usuario no tiene campo image).
